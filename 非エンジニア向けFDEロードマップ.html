はじめに：このロードマップが解く問題

FDE InterviewCat の原典（第1〜6章＋コーディング5題）は、現役SWEがBuilder FDE面接を突破することを前提に書かれています。そのため、非エンジニア（PdM、コンサル、営業、BizDev、CS、業務改善担当、データアナリスト、デザイナーなど）が同じ順番で読むと、第3章のコーディング演習や第4章のデバッグ系システムデザインで早々に詰まります。

このロードマップは、非エンジニアが「曖昧な顧客課題を技術で解く力」を可視化し、面接通過レベルまで引き上げるための再構成版です。前提として置く現実は3つあります。

  1. トップAIラボのBuilder FDEに最短距離で届くのは難しい。狙うべき第一の入口は、日系AI企業のFDE／AIソリューションエンジニア／Sales Engineer+型FDE／AI導入コンサル兼実装担当である。
  2. 非エンジニアの最大の武器は「顧客課題理解」と「曖昧さへの耐性」。原典が繰り返し示すとおり、FDEはアルゴリズム力ではなく現場の曖昧さを前に進める力で評価される。非エンジニアはこの土台をすでに持っている。
  3. コードが書けないままでは絶対にFDEにはなれない。少なくとも「LLM APIを叩き、データを保存し、ツールを呼び、READMEに設計判断を書ける」レベルは必須。逆に言えば、そこまでで十分。
このロードマップを完走すると、最低でも次の状態になります。
  • LLMを使った旗艦プロジェクトが1つGitHubにあり、READMEで設計判断を語れる
  • 第3章のコーディング5題のうち、AI寄りの3題（LLM CLI、会話履歴、ツールディスパッチャー）をゼロから実装できる
  • 第4章のデバッグ形式の面接で「仮説→検証→切り分け」を口に出せる
  • 第5章の行動面接4テーマを、自分の非エンジニア経験から語れる
  • 日系AI企業／Sales Engineer+型FDE／AI Solution Engineerに現実的に応募できる

第0部：FDEで証明すべき6つの力と非エンジニアの勝ち筋

FDEはコードを書けるコンサルでも顧客対応できるSWEでもなく、顧客の曖昧な課題を、動くAIシステムに変える役割です。書類と面接で証明すべき力は以下の6つに集約されます。

軸求められる状態非エンジニアの武器補うもの
顧客理解業務課題、制約、ステークホルダーを構造化できるヒアリング、提案、PM、コンサル経験技術要件への翻訳
実装力小さなバックエンド、CLI、AIアプリを作れる業務理解を仕様にできるPython／TypeScript、Git、API、DB
AI/LLM理解RAG、Function Calling、コンテキスト管理、Evalを説明・実装できるユースケース設計、効果定義LLM API、ツール実行、評価
システム設計現実的な制約下でアーキテクチャを選べる課題整理、優先順位付け、ROI判断DB、キュー、認証、監視、スケーリング
デバッグ仮説駆動でログ・メトリクスを取りにいける問題分解、現場対応OOM、レート制限、ネットワーク、DB負荷
コミュニケーション技術を非技術者に翻訳し、プロダクト改善に戻せる非エンジニアの最強領域技術的な正確さ
非エンジニアが面接で勝つのは、6軸すべてを満点にすることではありません。「顧客理解」「コミュニケーション」を満点に保ったまま、「実装力」「AI/LLM理解」を“議論できる最低ライン”まで持ち上げ、「システム設計」「デバッグ」は自分のプロジェクトの範囲だけ深く語れる状態を作ることです。

出身タイプ別の勝ち筋

出身武器落とし穴重点強化

業務改善／RPA業務フロー設計、現場巻き込みスクリプトレベルで止まるバックエンド／DB／LLMアプリ実装
データアナリストSQL、データ理解、可視化プロダクション運用経験が薄いAPI/エラー処理／本番設計を学ぶ

Phase 0方向決め（1週）

最初の1週間で、FDEの型と自分の入口を確定します。第1章で示された3タイプを、非エンジニア視点で再評価します。

タイプ内容非エンジニアからの現実度最初の入口として
Builder FDE顧客先でAIシステムを実装・本番導入。コード70〜90%短期は難、目標として置く中期目標

Internal Tools Builder社内DX／業務改善のAI化高い、実績作りに最適◎旗艦実績の作り方

非エンジニアの勝ち筋は「自分はエンジニアと同じ土俵で書けます」ではなく、「顧客課題を深く理解し、AIプロトを自分で作り、エンジニアと同じ語彙で議論できます」という立ち位置を作ること。

Phase 1技術基礎（4週）

ここでの目的は、立派なエンジニアになることではなく、「APIを叩き、データを保存し、エラーを扱い、READMEを書ける」状態になることです。LeetCodeはしません（理由は第6部）。

Week 1：開発環境とCLI

学ぶ：

  • ターミナルの基本（cd、ls、pipe、環境変数）
  • Git／GitHub（clone、commit、push、PR）
  • VS CodeまたはCursor（AI補完を必ず使う）
  • PythonまたはTypeScript（どちらかに絞る。AI寄りはPython推奨）
  • JSON、.env、設定ファイル

作る：

  • CSVを読み込んで整形し標準出力に書き出すCLI
  • エラー時に人が読めるメッセージを出す
  • READMEに使い方と失敗ケースを書く

合格ライン：

  • git clone → commit → push をストレスなくできる
  • コマンド一発で自分のスクリプトを実行できる
  • 失敗ケースをREADMEに3つ以上書ける

Week 2：APIとHTTP

学ぶ：

  • HTTPメソッド（GET／POST／PUT／DELETE）
  • REST API、ステータスコード（特に2xx／4xx／5xx）
  • JSON request／response
  • APIキー、Bearerトークン
  • タイムアウト、リトライ、429／503の意味

作る：

  • 外部API（天気、為替、GitHubなど何でも可）を呼ぶCLI
  • 失敗時に指数バックオフでリトライする処理
  • APIキーは.envから読む

合格ライン：

  • APIレスポンスを構造化して扱える
  • 429と503の違いを自分の言葉で説明できる
  • 「本番ならどう改善するか」をREADMEに書ける

Week 3：DBと永続化

学ぶ：

  • SQL基本（SELECT／INSERT／UPDATE／DELETE）
  • テーブル設計、主キー、外部キー、一意制約
  • SQLiteまたはPostgreSQL（どちらでも可、SQLiteが最速）
  • インデックスの意味

作る：

  • 顧客問い合わせを保存する小さなチケット管理API
  • ステータス、担当者、優先度、期限、検索条件
  • 同じメールアドレスからの重複登録は一意制約で防ぐ

Week 4：テストと小さな設計

学ぶ：

  • ユニットテスト（pytest または vitest）
  • 境界値テスト
  • 例外処理、ログ出力
  • 関数とクラスの責務分割

作る：

  • Week 3のAPIにテストを追加
  • 正常系、異常系、境界値を含める
  • 構造化ログ（JSON Lines形式）を出す

Phase 2要件定義と設計（3週）

第3章の冒頭に明記されているとおり、FDEのコーディング面接は「問題の理解」「要件の明確化」「最終要件」から必ず始まります。いきなりコードを書く人より、最初に曖昧さを潰せる人が評価されます。非エンジニアにとってここは最大の差別化ポイント。

身につける型（毎回この順で話す）

  1. 何を作るのか（What）
  2. 誰が使うのか（Who／ユーザー、システム間呼び出し、社内ツールか）
  3. 入力と出力は何か（Input／Output）
  4. 今回やる範囲とやらない範囲は何か（In Scope／Out of Scope）
  5. 失敗時にどう振る舞うか（Failure Mode）
  6. 本番なら何を追加するか（Productionization）

練習テーマ（原典のコーディング5題に対応）

各テーマで、コードを書く前に1ページの設計メモを書きます。

題材確認すべき曖昧さ
3.1 レートリミッター誰単位（user／API key／IP）で制限するか、超過時の挙動、グローバルかエンドポイント別か
3.2 LLM会話履歴サービスどのメッセージを残すか、トークン上限超えの戦略、systemは消さない、最新が大きすぎる時
3.3 フライト予約システム同一座席の二重予約、Seat Holdの挙動、キャンセル時の戻し方
3.4 LLM API CLIストリーミング表示、設定ファイル形式、プロバイダー切替、APIキーの扱い
3.5 ツールディスパッチャーバリデーション、並行実行、ツール失敗時の挙動、危険操作の制限

Phase 3LLMアプリ実装（4週）

FDE候補として最も見せやすい成果物は、LLMを使った小さな実用アプリです。原典では特に3.4／3.2／3.5が「FDEっぽさ」を示す課題として扱われています。

Week 1：LLM API CLI（3.4対応）

作る：

  • ターミナルでLLMと対話できるCLI
  • APIキーは.envまたは設定ファイルから読む
  • ストリーミング表示（response.text() で全部待たない）
  • OpenAI／Anthropic／ローカルOSS（Ollama等）を切り替えられる設計

見るべき観点：

  • なぜストリーミングが必要か（UX、メモリ、失敗時の損失）
  • 429／503への対応（指数バックオフ）
  • 会話履歴をどこまで保持するか（→ Week 2へ）
  • プロバイダー抽象（Strategy / Adapterパターン）

Week 2：LLM会話履歴サービス（3.2対応）

作る：

  • system（AIへの指示書）／user（ユーザー発言）／assistant（AI回答） メッセージを保存する
  • トークン上限を超えたら戦略に従って古いメッセージを削る
  • system は絶対に消さない
  • 最新メッセージが単体で大きすぎる場合は明示的にエラーにする

見るべき観点：

  • LLMはステートレス、履歴管理はアプリ側の責務
  • コンテキストウィンドウはコストと品質に直結
  • FIFO／重要度ベース／要約のトレードオフを口頭で説明できる

Week 3：AIエージェント・ツールディスパッチャー（3.5対応）

作る：

  • list_files、read_file、edit_file を登録する
  • LLMからのツール呼び出し要求を引数バリデーション
  • 複数ツールを並行実行（asyncio／Promise.all）
  • 失敗しても全体は落とさない。エラー文字列をLLMに返す（Graceful Degradation）

見るべき観点：

  • Function Callingの仕組み
  • 引数バリデーション（jsonschema、Pydantic）
  • 並行実行とタイムアウト
  • Human-in-the-loop（破壊操作の確認プロンプト）
  • サンドボックスディレクトリ外を編集できないようにする

Week 4：Evalと安全性

追加する：

  • 代表的な指示セット（10〜20件）を用意
  • エージェントが期待通りファイルを作るか自動検証するEvalスクリプト
  • サンドボックス外を編集できないことのテスト
  • READMEに制約、トレードオフ、本番化案を書く

合格ライン：

  • コマンド一発で make demo または docker compose up でデモできる （make＝コマンド集約ツール、docker＝環境ごとアプリを箱に詰めて動かす仕組み）
  • make eval でEvalが走り、合格率が表示される
  • 「AIが生成しただけ」ではなく、失敗・安全性・評価まで考えていることがREADMEから伝わる
非エンジニアの強み発揮ポイント：Evalの「指示セット」設計は、ユースケース設計力そのもの。ここで非エンジニアが圧倒的に強いことを面接で語れるようにする。

Phase 4システム実務力とデバッグ（4週）

第4章のシステムデザイン面接は、巨大SNSの設計ではなく、顧客環境の現実的な障害をどう切り分けるかが中心です。非エンジニアが最も苦手な領域なので、ここはじっくり時間をかけます。

Week 1：レートリミッター（3.1対応）

学ぶ：

  • Token Bucket、Sliding Window、Fixed Window
  • クライアント単位、エンドポイント単位の制限
  • 429、retry-after ヘッダ
  • メモリ肥大、クライアント数増加への対応

Week 2：予約システムと並行処理（3.3対応）

学ぶ：

  • 在庫管理、一意制約
  • 楽観ロック／悲観ロック
  • Seat Hold（TTL付き仮押さえ）
  • 状態遷移とイベント

Week 3：仮説駆動デバッグ（最重要）

第4章のデバッグ形式の面接は、面接官が情報を出し惜しみ、候補者から質問しないと進まない設計になっています。これが非エンジニアの最大の弱点。

練習するケース：

  • CSVインポートでOOMKilled（exit code 137）
  • 毎時0分に特定ノードだけ高負荷（Cassandraのホットパーティション）
  • LLM APIの429／503
  • ストリーミングレスポンスの途中切れ
  • RAGの検索精度低下

答え方の固定フォーム（必ずこの順で口に出す）：

  1. 観測事実の整理：「今わかっていることは◯◯と◯◯です」
  2. 仮説の列挙：「考えられる原因は3つあります。A、B、C」
  3. 検証順序の宣言：「最初に確認したいのは◯◯のログです。理由は◯◯」
  4. 絞り込み：「Aの可能性は低そうです。次にBを確認します」
  5. mitigation と root cause を分ける：「短期対応は◯◯、根本対応は◯◯」
  6. 再発防止：「同じことを起こさないために◯◯を入れます」

Week 4：アーキテクチャ Deep Dive

第6章でCohereが特に重視するスタイル。自分のポートフォリオ（フェーズ5）のアーキ図を、応募する企業のJDに合わせて選び直して語れるようにします。

合格ライン：

  • 技術選定を「流行っているから」ではなく、制約・コスト・運用で説明できる
  • mitigation と根本修正を分けて話せる
  • 顧客制約（オンプレ、閉域網、データ越境禁止）を設計に反映できる

Phase 5FDEポートフォリオ（4週）

非エンジニアの履歴書だけで「実装できる」と信じてもらうのは難しい。GitHub、README、デモ、設計図で補います。最低1つ、できれば2つの旗艦プロジェクトを作ります。

旗艦プロジェクト案A：顧客向けRAGアシスタント（おすすめ）

想定：

  • 顧客の社内ドキュメント、FAQ、規程、マニュアルを検索して回答
  • 非技術者にも使えるCLI／簡易UI
  • 回答に参照元を表示

必須要素：

  • ドキュメント取り込み（PDF／Markdown／Office）
  • チャンク分割／Embedding／Vector Search（Chroma、Qdrant、pgvectorなど）
  • LLM回答生成／回答評価（5〜10件の正解セット）
  • ハルシネーション対策（出典なしは答えない、信頼度閾値）
  • README

FDEらしい説明（READMEに必ず書く）：

  • 顧客は何に困っていたか
  • なぜファインチューニングではなくRAGか（第5章のメタファー「丸暗記 vs 辞書持ち込み」をそのまま使ってよい）
  • セキュリティ要件が強い場合のハイブリッド構成案
  • 本番ではログ、権限、監査をどう設計するか

旗艦プロジェクト案B：AIエージェント業務自動化

想定：

  • 顧客の問い合わせを読み、必要なツールを呼んで回答案を作る
  • CRM／FAQ／チケットDBのモックをツール化
  • 人間の承認を挟んで返信

旗艦プロジェクト案C：データ取り込み＆分析パイプライン

想定：

  • CSV／APIからデータ取り込み、DB保存、異常値検知、レポート
  • LLMで自然言語の分析サマリー

必須要素：バッチ／チャンク処理（OOM対策）、リトライ、データ検証、エラー行隔離、構造化ログ、レポート生成

ポートフォリオの最低条件

  • README（「何を作ったか」より「なぜそう設計したか」が中心）
  • セットアップ手順（コマンド一発で動く、make demo または docker compose up）
  • アーキテクチャ図
  • 主要な設計判断
  • トレードオフ
  • テスト／Eval
  • 失敗ケース
  • 本番化するなら追加する項目
  • 3分デモ動画またはスクリーンショット
第3章で繰り返し述べられるとおり、「環境構築で面接官を躓かせた時点で評価は地に落ちる」。README → clone → 1コマンドで動く まで揃えて初めて合格。

Phase 6面接対策（3週）

Week 1：コーディング面接（90分フォーマット）

非エンジニアは、AI文脈に近く達成感が出る順に進めます。

  1. 3.4 LLM API CLIクライアント
  2. 3.2 LLM会話履歴サービス
  3. 3.5 AIエージェント・ツールディスパッチャー
  4. 3.1 レートリミッター
  5. 3.3 フライトチケット予約システム

各問題は90分タイマーで練習。

時間やること
0-10分要件確認、スコープ確認、ユースケース列挙
10-20分エンティティ、API、データ構造を決める
20-60分最小実装（happy path）→ エラー処理
60-75分ドライラン、テスト、エッジケース
75-90分拡張性、トレードオフ、本番化の議論

面接では完璧な実装より、要件を明確にし、段階的に進め、最後に検証と拡張性まで語ることが大切。AIアシスタント（Claude Code、Cursor、Copilot）の使用は許可されることが多いですが、「AIに丸投げした提出物は即不合格」（第3章）なので、自分でレビューして堅牢性を加える時間を確保する。

Week 2：システムデザイン

3形式を準備：

  • デバッグ・トラブルシューティング（Cohere／Databricks型）
  • 自分のプロジェクトのArchitecture Deep Dive（Cohere／Palantir型）
  • AI／LLM特有のシステム設計（Sierra／OpenAI型）

優先お題：

  • RAGシステムを本番導入する設計（マルチテナント、権限、Eval、コスト）
  • 複数顧客向けLLMアプリのマルチテナント設計
  • LLM APIの高スループット処理（バックオフ、キュー、フォールバックモデル）
  • 顧客から「リクエストが失敗する」と言われた時のデバッグ（情報を引き出すターン）
  • CSV取り込みジョブが8GBファイルで落ちるケース（第4章 ケース1）
  • 毎時0分に特定ノードが高負荷（第4章 ケース2）

Week 3：行動面接

第5章の4テーマを、自分の非エンジニア経験に置き換えます。

テーマ自分の経験から拾うべき素材
顧客フィードバックのプロダクト還元顧客の声を一時対応ではなく仕組み／機能／規程に変えた経験
技術概念を非技術者に説明RAG／AI／データ／APIをビジネスの言葉で説明した経験。第5章の「丸暗記 vs 辞書持ち込み」型のメタファーを自分でも作れるか
優先順位付け複数ステークホルダーの要求をImpactとWorkaroundで整理した経験
エンタープライズ協業セキュリティ／法務／情シス／事業部の間に入って前に進めた経験

STAR＋Rテンプレ

  • Situation：顧客、事業、制約は何だったか
  • Task：自分が解くべき課題は何だったか
  • Action：どう分解し、どんな技術選択をしたか、なぜ他の選択肢を選ばなかったか
  • Result：顧客／事業／プロダクトにどんな影響が出たか（数字）
  • Reflection：今ならどう改善するか

第3部：質問する力を鍛える（非エンジニア最大の弱点）

第4章のデバッグ系面接で、面接官は意図的に情報を出し惜しみます。「リクエストが失敗します」だけ言われて、そこから候補者が自分で「ログを見せてください」「メトリクスは？」「Pod の終了理由は？」と聞き出さないと、面接は前に進みません。

非エンジニアは「相手に質問する」ことには慣れていますが、技術的に的確な質問には慣れていません。これを意図的に訓練します。

訓練法

  1. 第4章のケース1（CSVインポート→OOMKilled）を音読。候補者の発言だけ覚える。
  2. 友人または自分で、面接官役と候補者役を分けて再演。情報は段階的にしか出さない。
  3. 候補者役は、必ず「次に何を見たいか／なぜ見たいか」を口に出す。
  4. 5ケース全部を、合計10時間かけて反復。

よく使う質問テンプレ（暗記する）

  • 「まず観測事実を整理させてください。今わかっているのは◯◯と◯◯ですね？」
  • 「アプリケーションログにエラーやスタックトレースは出ていますか？」
  • 「コンテナの終了理由とexit codeを教えてください」
  • 「該当時間帯のCPU／メモリ／ディスクI/Oメトリクスを見たいです」
  • 「クラスタ全体で均等に悪化していますか、それとも特定ノードに偏りがありますか？」
  • 「データモデルの主キー／パーティションキーは何ですか？」
  • 「再現する最小条件は何ですか？」
  • 「これは初めて起きた事象ですか、それとも以前から潜んでいた可能性がありますか？」

これは技術知識というよりスクリプト。暗記して反射的に出るまで反復します。

最低限揃えるもの

第6部：やらなくてよいこと

非エンジニアが最初に時間を使いすぎると遠回りになるもの。この6つは意識的に避ける。

  • LeetCode Hardの大量演習：第3章で明記「DSAの重要度は極めて低い」。FDE面接ではほぼ出ない。Easy〜Mediumを軽く触る程度で十分。
  • 機械学習理論の深掘り：勾配降下法やトランスフォーマー内部実装をやる時間で、LLM APIをもう1つ呼べる。FDEは「LLMを使う側」であり「作る側」ではない。
  • 論文読み込み：RAG／Tool Use／Function Callingの概念がわかれば十分。論文サーベイは中期で。
  • Kubernetesの細部暗記：YAMLの細かい記法より、「コンテナがOOMで再起動する仕組み」「exit code 137の意味」「Pod／Node／Clusterの関係」が言える方が10倍重要。
  • 大規模分散システムの理論だけの学習：Twitter／YouTubeを設計する練習はほぼ無駄。FDEは現場の特定顧客の問題を解くロール。
  • きれいなUI作り込み：CLIで十分。READMEに動作スクショがあればよい。UIに時間を使うくらいなら、Evalセットを増やす。

将来的には全部役立ちますが、FDE選考でまず問われるのは、顧客課題を理解し、実用的なコードを書き、失敗ケースとトレードオフを説明できること。

第7部：詰まった時のリカバリプラン

「コードがどうしても書けない」

  • 旗艦プロジェクトを諦めて、既存OSS Agent（例：openai-agents-python、LangChain、LlamaIndex のサンプル）を fork してカスタマイズするルートに切替。fork元を明記したうえで、自分が加えた変更（プロンプト、ツール追加、Eval整備）を README に書く。
  • それでも詰まる場合、Sales Engineer+ ／ AI導入支援 ／ AI Solution Engineer に的を絞り、レジュメで「プロンプト設計＋業務翻訳＋プロト構築」を前に出す。

「英語が伸びない」

  • 外資ラボを一旦外し、日系AI企業＋外資の日本拠点（Databricks Japan、Salesforce Japan、Microsoft Japan のAI関連職）に集中。Cohereは英語比率が高めなので後回し。

「忙しくて週10時間取れない」

  • 90日プランを 180日に延長。順番は変えない。Week粒度ではなく月粒度で進める。
  • 旗艦プロジェクトを 1つ に絞る（推奨は案A：RAGアシスタント）。

「面接で落ちた」

  • フィードバックがある場合は1つだけ重点強化。
  • フィードバックがない場合の典型的な落ち方：
    • 要件定義をすっ飛ばしてコードを書き始めた → フェーズ2の1ページ設計メモを再徹底
    • デバッグで何も聞けず黙った → フェーズ4 Week 3を再走、質問テンプレを暗記
    • 行動面接が「調整しました」止まり → STAR の Action に技術判断を必ず1つ入れる練習
    • READMEに「動きます」しかなかった → トレードオフを3つ書き足す

最終ゴール

非エンジニアがFDEを目指すうえでの勝ち筋は、「自分はエンジニアと同じ土俵で競技プログラミングができます」ではありません。

勝ち筋は次の形です。

  • 顧客の業務課題を深く理解できる
  • 曖昧な要望を技術要件に分解できる
  • AI／LLMを使った小さなシステムを自分で実装できる
  • 失敗ケース、セキュリティ、運用、評価まで考えられる
  • 技術者にも非技術者にも説明できる
  • 現場の学びをプロダクト改善に戻せる

原典が繰り返し示すとおり、FDEで見られるのは難問アルゴリズム力ではなく、実務の曖昧さを前に進める力です。非エンジニアはこの曖昧さへの耐性をすでに持っていることが多く、そこに「小さく作れる実装力」を足せば、かなり強い候補者になれます。

24週間後、あなたは「コードを書ける非エンジニア」ではなく、「現場を理解しているエンジニア」として面接の席に座っています。
